# Бавария: дашборд Bitrix

PHP-страница только для авторизованного пользователя ID 5 (Оксана Шлегель). CRM, лиды и задачи читаются с её правами, без сервисного администратора, пароля, вебхука или `NOT_CHECK_PERMISSIONS`. Все входы защищены; ответы посылают `no-store`. Общий кэш веб-сервера/CDN для страницы недопустим.

Страница: `/dashboard-oksana-v1/`. Одиннадцать PHP-файлов: `bootstrap.php`, `index.php`, `api.php`, `view.php`, `task-data.php`, `date-range.php`, `lead-data.php`, `stage-history.php`, `activity-data.php`, `app.php`, `app-install.php`. Node.js и отдельный сервер приложению не нужны. Оформление использует Google Fonts (Inter), при недоступности — запасной шрифт.

## Даты

Два календаря «С» и «По», обе даты включаются целиком. По умолчанию — с начала текущего месяца до сегодняшнего дня. Несуществующие даты и обратный диапазон отклоняются. При смене дат сохраняются выбранные причины обращения, результаты и воронки. Для сравнения сделок берётся непосредственно предшествующий период такой же длины в днях. Даты интерпретируются в часовом поясе PHP/Bitrix сервера; в URL используются `from` и `to` в формате `YYYY-MM-DD`.

Сделки отбираются по дате создания. За выбранный и предыдущий периоды вместе допускается до 5000 доступных сделок: при превышении вместо неполных показателей выводится ошибка. Задачи — текущее состояние, независимо от периода; сервер считает полные итоги, списки выдаются по 50 записей.

## График лидов

График «Обращения из лидов» автоматически включает все варианты списка «Причина обращения» в порядке настройки Bitrix, даже с нулевым числом лидов. Множественный выбор причин содержит те же варианты; по умолчанию выбраны покупка новых авто и сервис. Новые значения появляются без изменения кода. Снятие всех галочек оставляет график пустым; выбор сохраняется при применении дат. Каждое значение учитывается отдельно по ID перечисления. Фильтры причины и результата относятся только к этому графику; фильтр результата не меняет знаменатель доли.

Поле-список `CRM_LEAD` определяется по единственной русской подписи «Причина обращения». Для «Покупка нового автомобиля» (или прежнего «Покупка автомобиля») и «Сервис» сохраняется проверка целевой конвертации в категории 0 и 7 соответственно. Для остальных причин показываются успешные (`S`), неуспешные (`F`) и открытые (`P`) лиды. Доля успешных для этих причин определяется только статусом лида и не означает попадание в нужную воронку. Наличие двух исходных вариантов больше не обязательно. Отсутствие или неоднозначность поля выводит ошибку только в блоке лидов.

Выбранный период относится к **дате создания лида**. Используются текущие статусы и текущая причина обращения. Исторические изменения причины не восстанавливаются и новые поля/обработчики в Bitrix не создаются.

- **Целевой:** лид успешен (`S`) и связан через `LEAD_ID` с доступной пользователю сделкой правильного направления: покупка авто → категория `0` («Продажа новых авто»), сервис → категория `7`. Состояние самой сделки не влияет на факт квалификации лида. Сделка может быть создана позже выбранного периода.
- **Неуспешный:** лид имеет семантику отказа `F`.
- **В работе:** лид имеет семантику `P`; это не отказ.
- **Не подтверждено:** лид успешен, но доступная связь со сделкой правильной категории не найдена. Другая воронка или отсутствие прав на связанную сделку не подменяются отказом.

Один лид считается один раз, даже при нескольких связанных сделках. 10 лидов по покупке авто и один целевой дают 10% конверсии. Неуказанные и неоднозначные причины показываются отдельным числом и не распределяются произвольно между вариантами. Лиды и связи со сделками читаются порциями с проверкой прав.

## Накопительная воронка сделок

Кружок и итоги успешных/проваленных сохраняют текущие статусы выбранной когорты. Основная воронка накопительная: для каждой уникальной сделки определяется максимальный достигнутый основной этап по текущему статусу и доступной истории этой воронки. Все предыдущие основные этапы засчитываются, даже если их пропустили прямым переводом. Повторные заходы и возвраты назад не увеличивают счётчики и не уменьшают достигнутый максимум.

Первая строка показывает общее число вошедших сделок. Дальше отображаются переходы A → B и отношение накопительных количеств: 100 → 80 → 50 → 30 дают 80%, 62,5% и 60%. Полосы показывают накопительное количество относительно первого этапа; проценты — конверсию относительно предыдущего. Без базы сравнения показывается «—», а не 0%. Клик открывает ту же накопительную группу, включая сделки с пропущенными этапами.

Успех сейчас или в сохранённой истории засчитывает весь основной путь. Провал не засчитывает поздние этапы сам по себе: используется наибольший известный основной этап до провала. «Отложено» — отдельная боковая ветка: категория 0, код 12, либо одноимённые этапы «Отложено», «Отложил покупку», «Отложенная покупка». Она не входит в основной порядок и не засчитывается успешно дошедшим сделкам. Число «Отложенные» рядом с успешными и проваленными считается отдельно: только текущее значение «Отложенные» пользовательского поля «Статус сделки» в выбранной воронке и периоде создания сделки. Стадия «Отложил покупку» не подменяет это поле. Нажатие открывает ровно эти сделки. Если поле неоднозначно, отсутствует или не содержит нужного варианта, вместо нуля показывается предупреждение и прочерк.

Порядок и семантика этапов берутся из текущей настройки Bitrix. История читается только для сделок, разрешённых CRM API пользователю 5, и только для текущей воронки. Дата периода относится к созданию сделки. Накопительное прохождение пропущенных этапов — согласованное правило расчёта, а не утверждение о наличии событий в журнале. Если запись ранних этапов отсутствует, используется максимальный известный этап; ветки после провала не додумываются. При технической ошибке чтения истории промежуточные проценты не показываются, кружок и итоги сохраняются.

`node tests/funnel.cjs` проверяет фактические JS-функции из `view.php`: пример 100→80→50→30, прямые скачки, возвраты, повторы, уникальность сделок, успех/провал, отложенную ветку, совпадение детализации с накопительными числами и ограничение конверсии 0–100%. Node нужен для этого теста, не для работы страницы.

## Остальные показатели

Успех комиссионной сделки означает успех стадии, а не продажу автомобиля. Успех сервиса означает запись, а не выполненный ремонт. Суммы сделок — `OPPORTUNITY` в KZT, не поступления оплаты. При другой валюте выводится ошибка. Телефоны, поля автомобиля и заказ-наряды 1С не подключены. Пустые источники скрываются. Переходы воронки идут в порядке Bitrix: сначала видны шесть пар этапов, остальные раскрываются отдельно. Успешные и проваленные вынесены в итоги. Для накопительной воронки используются доступная история и текущая стадия сделки.

## Обновление на сервере

Из SSH пользователя `bitrix`:

```bash
git -C /home/bitrix/bavaria-dashboard-stage pull --ff-only
bash /home/bitrix/bavaria-dashboard-stage/deploy-dashboard.sh
```

Если `git pull` завершился ошибкой, остановиться. Скрипт проверяет PHP-синтаксис и автономные тесты, готовит копию страницы с сохранением дополнительных пользовательских файлов, затем переключает только каталог дашборда. Полная резервная копия остаётся вне корня сайта по адресу, напечатанному скриптом. При неудачном переключении предыдущая версия восстанавливается автоматически. Источники Bitrix и записи CRM не меняются. Не копировать `.git`, тесты и shell-скрипт в корень сайта.

После обновления войти как Оксана, проверить обе даты, значения поля и показатели на небольшом известном наборе лидов. Сверять по исходным лидам и связанным сделкам, а не по дате создания сделки. Проверить другие аккаунты и приватное окно: ни страница, ни API не должны возвращать данные дашборда. Стандартная страница входа Bitrix допустима. Автономные тесты не проверяют реальную реализацию API и права рабочего Bitrix.

## Показатели и таблица сервиса

В круге, верхней карточке сервиса и заголовке вкладки «Сервис» показано число успешных лидов (`STATUS_SEMANTIC_ID=S`) с причиной «Сервис», созданных в выбранный период. Это сумма целевых и успешных без подтверждённой связи со сделкой; права на связанную сделку не меняют статус самого лида. Доля круга — успешные сервисные лиды / все сервисные лиды. При ошибке чтения лидов число заменяется прочерком. Фильтры полосок причин и воронок сделок не меняют этот показатель.

Таблица сервиса остаётся списком разрешённых сделок категории 7 с прежними фильтрами. Колонки «Модель», «Причина обращения», «Запись не состоялась по причине» читаются из пользовательских полей `CRM_DEAL` по единственной русской подписи. Значения списков расшифровываются через ID перечисления. Отсутствующие, неоднозначные и неподдерживаемые поля отображаются прочерком с предупреждением; код не угадывает UF-коды и не изменяет настройки CRM. Число сделок таблицы и число записей выведены отдельно от успешных лидов.

## Проверки

`php tests/tasks.php` проверяет 2607 искусственных задач: полные итоги, фильтры, курсорные страницы и передачу параметров прав.

`php tests/leads-and-dates.php` проверяет даты, високосные дни, границы суток, причины обращения, порции по 500 лидов, повторные сделки одного лида, нужную категорию, отказы и незакрытые лиды, конверсию за пределами периода создания лидов, неоднозначность поля и передачу параметров прав. Использует искусственный Bitrix API.

Локально выполнены PHP 8.2 (WebAssembly) lint и автономные тесты, браузерные проверки дат/графика/фильтров/экранирования/отказа API и тест переключения каталогов с восстановлением после ошибки. Проверка новых полей и цифр на рабочем сервере требует установки пользователем.

`php tests/stage-history.php` проверяет ограничение истории разрешёнными ID сделок, воронку, временной порядок событий, повторные посещения, пустую когорту, неизвестную схему и порции по 500 ID. Использует искусственный ORM. Реальные поля истории Bitrix необходимо проверить после установки.

## Отчёт по CRM-делам во вкладке «Задачи»

Отдельный отчёт повторяет структуру присланного образца: ответственный, просроченные, сегодня, завтра, 2–3 дня, 4–7 дней, сделки без дел, активные сделки, всего дел. Есть фильтр ответственного, цветовые отметки и строка итогов. Это текущий срез по активным сделкам выбранных воронок, независимо от периода создания, выбранного вверху страницы.

Учитываются только доступные пользователю 5 незавершённые CRM-дела, связанные с доступными активными сделками через штатную таблицу связей. Отдельный модуль задач не подменяет CRM-дела. Одно дело с несколькими связями считается один раз. Сроки — календарные непересекающиеся интервалы в часовом поясе сервера: до сегодня, сегодня, завтра, второй–третий и четвёртый–седьмой день. В общем числе дел остаются также дела без срока и позже недели. Завершённые и недоступные дела не учитываются.

Сделки и сделки без доступных незавершённых дел считаются по ответственному сделки, дела — по ответственному дела; эти ответственные могут различаться. Ошибка отчёта не блокирует список задач, доступна повторная загрузка. Кнопки создания/добавления и постановки задач удалены со всех экранов; статус задачи отображается без интерактивной кнопки.

`php tests/activities.php` проверяет интервалы сроков, фильтр воронок, исключение закрытых/недоступных дел, разные ответственные, повторные связи одного дела, сделки без дел и итоги на искусственном API Bitrix.

## Приложение Bitrix

Подготовлены защищённый обработчик `app.php` и страница первоначальной установки `app-install.php`. Регистрация приложения в вашем портале пока не выполнена. Инструкции и точные адреса — в [BITRIX-APP.md](BITRIX-APP.md). Установочную страницу может открыть администратор, но она не читает показатели; дашборд и все API продолжают требовать пользователя 5. В приложении используется официальный SDK для высоты окна. Обычная страница `index.php` сохраняется.

`php tests/deal-fields.php` проверяет разрешение пользовательских полей сделок, списки, отсутствие/неоднозначность и вариант «Отложенные» без подмены стадией. `node tests/lead-chart.cjs` проверяет выбор нескольких причин и настройки по умолчанию.
